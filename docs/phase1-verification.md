# Phase 1 connected verification

This pass used the connected Supabase project and the existing isolated authorization-test businesses A and B. It did not use real customer accounts. The normal signup endpoint returned `429 over_email_send_rate_limit`, so fresh-signup and fresh-onboarding browser checks remain unverified. Two existing test account password hashes were backed up, temporarily changed to allow sign-in, restored afterward, and compared byte-for-byte with the backups. Temporary credential and token files were cleared. A test booking was cancelled after the checks.

## Passed

- Seven authenticated authorization integration tests passed: owner analytics, cross-business rejection, manager analytics permission, manager billing denial, anonymous public booking projection, and direct RPC execution denial for anonymous and authenticated callers.
- The public booking projection loaded business A's published service and staff. Availability with an empty add-on **array** returned 191 slots over the requested date range. With an object it failed with PostgreSQL `22023` (`cannot extract elements from an object`). The public booking and dashboard callers now send arrays.
- Public hold, confirmation, and management-token issuance succeeded. Repeating confirmation with the same request key returned the same appointment. A second hold on its occupied staff slot was denied with `P0409`.
- The owner workspace snapshot contained the confirmed booking. Before repair, the snapshot failed with `42703` because `forms.archived_at` does not exist. The deployed Edge query now filters `forms.status != archived`, and the snapshot loaded successfully.
- The customer management link loaded the booking and moved it from 09:00 to 09:30 UTC. Cancellation changed the appointment and session to cancelled and marked its reservation inactive.
- Business B initially had no scheduling fixture. A separate verification staff member, service, hours, and published booking page were added to this isolated test business. Public projections for A and B returned different page IDs. B offered 16 slots on November 9; a public hold and confirmation worked, repeated confirmation returned the same appointment, and customer-link cancellation left the appointment/session cancelled with zero active reservations. The verification fixture remains for repeatable tenant checks; two test appointments were cancelled.
- B owner dashboard booking created an appointment at 11:00 UTC on November 9, moved it to 11:30, and rejected a second move using stale row version 1 with HTTP 409 / `P0409`. Dashboard cancellation left row version 3, appointment/session cancelled, and zero active reservations. The isolated owner's password hash was restored after the check.
- Local browser testing showed the public service and available times, owner A and owner B dashboards, the cancelled booking in owner A's Bookings table, and the multi-business switcher. Account B could switch from its owner workspace to business A as a manager; that view exposed only Booking Page and Analytics, matching its permission flags. The selected business persisted across a page reload. The browser account was signed out.
- A temporary staff membership and profile link for the isolated account loaded the `/staff` browser schedule for business A; it could not open the owner/manager workspace for that membership. This exposed cancelled bookings under “upcoming.” Edge version 58 now returns only current or future sessions with pending/confirmed/checked-in appointments and only those customers. A connected follow-up returned one confirmed session and one customer instead of six sessions/six customers. The original manager membership, profile link, and password hash were restored and verified.
- Authenticated dashboard booking created a test appointment through the live Edge action and the shared hold/confirmation engine. The first dashboard cancellation left its session state as `scheduled` despite releasing the reservation. Dashboard cancellation now calls the transactional `cancel_appointment` RPC; a second connected test returned appointment `cancelled`, session `cancelled`, and reservation inactive. Both test appointments were cancelled, and the earlier test session was brought into the same cancelled state. The test owner's password hash was restored.
- TypeScript, production build, and the six existing unit tests passed before final documentation. The seven connected authorization tests passed when isolated test tokens were supplied.

## Defects found and repaired

1. Booking callers passed `{}` for `p_addon_quantities`, although the database functions call `jsonb_array_elements`. Public availability, public hold, and dashboard hold now pass `[]`.
2. Workspace snapshots queried nonexistent `forms.archived_at`; they now exclude forms with `status = archived`.
3. A user with two full-workspace memberships could see only the oldest membership. An authenticated Edge action now lists authorized full-workspace businesses, and the dashboard can switch among them.
4. The public management page sent `p_management_token` to the Edge action, but the RPC expects `p_token`. A B booking reproduced `PGRST202` after confirmation. Edge version 63 translates the parameter for `get_managed_appointment`. The second B booking loaded through the management link and was cancelled with that link.

## Migration repair

- Rescheduling initially moved the session time but left `appointments.row_version` at 1. Cancellation then advanced it to 2. Because the reschedule RPC checks the appointment version, a stale second reschedule could pass the same version check. Lovable applied migration `20261108070142_0fe03de6-2094-4853-94cf-548a4f1db425.sql`: its connected rollback-only check found that a successful move now advances the version by one, an old version is rejected with `P0409`, and the current version succeeds. The generated migration included fixture-dependent test blocks; with Eric's approval those blocks were removed from the Git file, leaving only the already-applied repair. The exact return anchor exists in the preceding migration and no fixture IDs remain. A clean-database replay has not been run because a local Supabase/Docker environment is unavailable.

## Still open before the full phase is signed off
- Fresh signup and browser onboarding could not be exercised while Supabase's email-send rate limit was active. Existing onboarding database checks are documented separately in `authorization-verification.md`.
- Invitation redemption with fresh staff and manager accounts and the broader 50-scenario acceptance suite remain unverified. Staff browser schedule visibility was tested with a temporary isolated fixture, not a fresh invitation.
- The booking interface was tested in the local browser against the live backend. The published `bookingsoftware.lovable.app` public booking page also loaded the isolated business A service and displayed 09:00–16:30 UTC slots on Monday, November 9. A hosted authenticated dashboard smoke test remains open.
- At a 390×844 browser viewport, the hosted public booking page retained a 350-pixel main content area within the 390-pixel body, with no horizontal document overflow. The service/back control, date choices, time slots, and reserve control remained in the accessibility tree. The browser viewport override was reset afterward. This is a narrow public-booking layout check, not a full mobile dashboard or accessibility audit.
- The hosted invalid booking URL showed its loading state followed by “Booking unavailable.” It also exposed the generic transport error text. The shared backend client now reads the response body from Supabase function errors, and `P0404` maps to “This booking page is not available.” The user-facing fix passed typecheck/build; hosted publication still needs confirmation.
- The date strip now constructs dates in the booking location's timezone rather than the visitor's local timezone. A local browser test temporarily set the isolated fixture location to `Pacific/Kiritimati`: while the visitor's date was November 5, the first offered business date was Friday, November 6. The fixture location was restored to `UTC` immediately afterward. This checks date labeling, not the database's DST transition rules.

## Daylight-saving guard

- Edge `backend-api` version 61 rejects invalid calendar dates, spring-forward local times that do not exist, and fall-back local times that occur twice. Four focused tests exercise the deployed converter's source for ordinary conversion and each rejection case in `America/New_York` and `UTC`.
- With B's **business** timezone temporarily set to `America/New_York`, the deployed blocked-time action rejected March 14, 2027 at 02:30 as nonexistent and November 7 at 01:30 as ambiguous; an ordinary 09:30 block succeeded. The account hash, business timezone, and block state were restored afterward.
- With B's **location** timezone temporarily set to `America/New_York` and Sunday hours 00:00–04:00, live availability returned six spring slots, skipping 02:00–02:59, and ten fall slots, including two different 01:00/01:30 instants. A public booking on spring 03:00 and the second fall 01:00 each confirmed and then cancelled via its management link. Location timezone, Sunday hours, and the advance window were restored; neither test appointment remains active. Slot labels now include EDT/EST so the repeated hour is distinguishable.

Edge `backend-api` version 63 contains the snapshot repair, dashboard empty-add-on fix, membership listing, scoped-schedule filtering, transactional dashboard cancellation, daylight-saving guard, and management-token mapping. Its `verify_jwt=false` setting is retained for public actions; the function verifies bearer tokens for authenticated actions.
